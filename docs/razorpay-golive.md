## The thing that actually blocked a test payment — 31 Jul

**Symptom, reported from the attempt: "the website was not listed" on the
Razorpay side when trying to pay.**

That is almost certainly Razorpay's **approved-website / authorised-domain**
check, and if so it is **expected right now and not a bug in our code**.
Razorpay Checkout only opens for an origin registered against the merchant
account. Today the app is reachable at `http://13.234.85.127/` — a bare IP,
over plain HTTP — and the approved entry is the domain. An IP origin is not the
approved website, so checkout has nothing to match.

**This does not get fixed on our side. It clears at DNS cutover**, when the app
starts answering on `https://www.quadishotels.com`. Payments and go-live are the
same task; they cannot be finished in either order independently. Do not go
hunting in `RazorpayService` for this one.

**Both dashboard-side possibilities were checked on 31 Jul and both are fine:**

| Checked | Answer |
|---|---|
| Which merchant account | **Feb '26** "QUADIS SERVICES PRIVATE LIMITED" — the right one, the one whose live keys we hold. Not the Sept '21 duplicate |
| Website approved and listed | **Yes, confirmed present** |
| Live mode | Verified 29 Jul — Test Mode off, KYC complete |

So the domain approval exists; the **origin we tested from** was not it. The
gateway behaved correctly and rejected an unregistered origin. Nothing further
is owed on the dashboard except the webhook URL below.

If checkout still reports the website at cutover, the one thing worth
re-checking is whether the approved entry is the **apex only**. `www` is her
canonical host (AGENTS.md §3a) and is where checkout actually runs — an entry
covering only `quadishotels.com` can still fail at `www.`. Cheap to confirm,
and it is the last remaining variant of this failure.

| Piece | State |
|---|---|
| Live `rzp_live_` keys in SSM | ✅ |
| Webhook URL `https://www.quadishotels.com/api/webhooks/razorpay` | ✅ Enabled |
| Subscribed events | `payment.authorized`, `payment.failed`, `payment.captured`, `order.paid` |
| **Automatic Capture** | ✅ on — captures within 12 min of bank authorisation |
| Signature verification | ✅ proven, see below |
| `create-order` on live site | ✅ `isSimulated: false` |

**`payment.authorized` is subscribed but NOT handled by our code** —
`routes/webhooks.ts` acts only on `order.paid`, `payment.captured` and
`payment.failed`. Harmless, but it is not a substitute for Automatic Capture;
if capture were Manual the booking would never confirm no matter what is
subscribed.

**Signature verification was proven without a real payment**, by signing a
payload with the secret from SSM and posting it at the live endpoint:

- correctly signed, nonexistent booking code → **404 "Target booking not
  found"** — the HMAC passed and the request reached the booking lookup
- deliberately wrong signature → **401 "Invalid Razorpay webhook signature"**

⚠️ **What that does NOT prove:** it signs with *our* copy of the secret, so it
cannot tell you whether *Razorpay's* stored copy is the same string. If they
differ, real deliveries 401 and paid bookings never confirm. Only a real
payment settles it — check the delivery log. This is the single remaining
unknown in the payment path.

## Setting the three SSM parameters

`install.sh` already reads them and writes `/etc/quadis/api.env`; nothing in the
repo needs editing. Set them once, then redeploy:

```bash
aws ssm put-parameter --region ap-south-1 --type SecureString --overwrite \
  --name /quadis/razorpay-key-id        --value 'rzp_live_...'
aws ssm put-parameter --region ap-south-1 --type SecureString --overwrite \
  --name /quadis/razorpay-key-secret    --value '...'
aws ssm put-parameter --region ap-south-1 --type SecureString --overwrite \
  --name /quadis/razorpay-webhook-secret --value '...'

./deploy/build-artifact.sh && ./deploy/push.sh
```

Sanity-check the lengths first — `23 / 24 / 64` — and confirm the key begins
`rzp_live_`:

```bash
printf 'id=%s secret=%s webhook=%s\n' "${#RZP_KEY_ID}" "${#RZP_KEY_SECRET}" "${#RZP_WEBHOOK_SECRET}"
curl -s -o /dev/null -w "auth: %{http_code}\n" \
  -u "$RZP_KEY_ID:$RZP_KEY_SECRET" "https://api.razorpay.com/v1/payments?count=1"
```

Never print the whole env file or an unfiltered `get-parameter` — both echo
secrets in plaintext.

## Three guards added 31 Jul, so the old traps cannot repeat silently

The previous version of this file asked a human to check these by eye. They are
enforced now:

1. **A test key can no longer masquerade as live.** `RazorpayService` used to
   reject only the literals `mock` and `rzp_test_simulated` — so a genuine
   `rzp_test_…` key passed and ran checkout against Razorpay's *test*
   environment, looking perfect and moving no money. Under `NODE_ENV=production`
   the key must now begin `rzp_live_` or the service stays simulated and logs
   why.
2. **The webhook secret fails closed.** It used to fall back to the literal
   `'secret_simulated_webhook'` — **published in this public repo**. With
   `RAZORPAY_WEBHOOK_SECRET` absent in production, anyone could HMAC a payload
   with it and mark any booking CONFIRMED/PAID without paying. In production
   there is no fallback; a missing secret rejects every webhook.
3. **`install.sh` refuses a half-configured deploy.** A key without a webhook
   secret is the worst state — the guest is charged and the booking never
   confirms — so that combination is now fatal at install time, and a
   non-`rzp_live_` key prints a warning.

Also fixed, and it is a payment bug rather than a hygiene one: **`trust proxy`
was unset**. Behind nginx every request looked like `127.0.0.1`, so all guests
shared one 100-request/15-minute rate-limit bucket, while
`awaitServerConfirmation` polls up to 36 times per checkout. A few simultaneous
guests would 429 each other *after* paying. `app.ts` now trusts exactly one hop.

## Verifying, after cutover

`isSimulated: false` is the proof that the API is really live:

```bash
CODE=$(curl -s -X POST https://www.quadishotels.com/api/bookings/initiate \
  -H 'Content-Type: application/json' \
  -d '{"propertySlug":"hotel-quadis-sector-51-noida","roomTypeSlug":"deluxe-room",
       "checkIn":"2026-08-10","checkOut":"2026-08-11","roomsCount":1,"guestsCount":1,
       "guestName":"Test Booking","guestPhone":"9999999999"}' \
  | grep -o '"booking_code":"[^"]*"' | cut -d'"' -f4)

curl -s -X POST https://www.quadishotels.com/api/payments/create-order \
  -H 'Content-Type: application/json' -d "{\"bookingCode\":\"$CODE\"}"
```

The hold expires by itself in 15 minutes.

### The real test

A CLI check cannot prove the chain. Make one **real booking on a phone**, pay by
UPI, and watch it flip to CONFIRMED inside the 90-second poll. Then refund it
from the dashboard. There is no ₹1 option — the amount comes from the rate
sheet, so the cheapest is one night at Quadis Sector 51 (₹1,500 base).

If it pays but never confirms, open **Razorpay → Webhooks → delivery log**:

- **401** — the secret does not match `RAZORPAY_WEBHOOK_SECRET`
- **404** — the event carried no `bookingCode` we could resolve
- **connection error / nothing** — the webhook URL is still the dead CloudFront
  one, or DNS has not cut over
- **nothing at all, and the URL is right** — Payment Capture is on Manual, so
  only `payment.authorized` fired and we do not handle it. Set it to
  **Automatic**.

## No longer relevant

**The CloudFront API-masking bug is gone with CloudFront.** It used to turn
every API error into 200 `text/html`, so `handlePayNow` threw
`Unexpected token '<'` at the guest instead of showing the real error. nginx
proxies `/api/` straight to the Node process and never rewrites its responses,
so the `quadis-spa-router` CloudFront Function that was built to fix it is not
needed. Verified on the box: `/api/…` returns JSON with its true status code.
