FOR YOU BEFORE SENDING
----------------------

Photo editing is being built right now. It is NOT live yet - do not tell them
they can change photos today.

The code is written against a storage "adapter", so whichever they pick is a
config change, not a rewrite. If they do not reply within a few days, we go
with S3, because that account already exists and nothing is blocked.

My own recommendation is Cloudinary, and the reason is bandwidth cost, not
features - see the note at the bottom.

-------------------------------------------------------------
WHY I RECOMMEND CLOUDINARY - REASONING, NOT FOR THE CLIENT
-------------------------------------------------------------

It is a bandwidth question, not a features question.

The site currently ships 558 MB of images, with single PNGs up to 3.45 MB.
S3 storage is trivially cheap; S3 *egress* is not - roughly $0.09/GB. Every
visitor loading a gallery pulls real money through that meter, and the bill
scales with exactly the thing the client wants more of.

Cloudinary's free tier covers 25 GB of delivery a month and transforms images
on the fly - correct size, modern format, served from a CDN. That fixes the
558 MB payload as a side effect rather than as a separate project.

S3 can match it, but only with CloudFront in front and a resize step we write
and maintain ourselves. That is more moving parts for a worse outcome.

If they pick S3 anyway it is fine - the adapter makes it a one-line switch,
and CloudFront can be added later to bring the egress cost back down.
